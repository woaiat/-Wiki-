# AGENTS.md

## 项目目标

这个仓库是一个由 LLM 持续维护的个人高维 wiki。

目标不是简单保存资料，而是把原始资料逐步整理成可查询、可交叉引用、可持续更新的知识库。
回答问题时，优先基于已经沉淀的 `wiki/`，而不是每次重新翻原始材料。

## 当前目录职责

- `raw/`
  - 放原始资料，是事实来源。
  - 原始资料默认只读，不做内容改写。
  - 这里就是当前主输入层，按主题并列展开。
  - 当前常见顶层包括：
    - `self/`
    - `二次元/`
    - `学习流/`
    - `高等数学/`
    - `线性代数/`
    - `Linux/`
    - `C++/`
    - `数据结构与算法/`
    - `思政/`
    - `即兴伴奏-流行键盘/`
    - `增量游戏/`
    - `markdown语法/`
    

- `wiki/`
  - 放 LLM 整理后的 markdown 页面。
  - 这里才是长期维护的知识层。
  - 当前主维护方向是：
    - `自我/`
    - `学习/`
    - `兴趣/`
    - `sources/`
  - 科研不再放在这个仓库里；如果后续涉及科研，默认视为独立工作区内容，而不是本仓目录。

- `schema/`
  - 放这个项目的参考方法和后续规则材料。
  - `schema/README.md` 是总体思路参考，不是唯一执行规则。
  - 当前真正优先执行的是本文件。

## 页面层级

### 1. raw

原始文件层，只保存输入材料。

### 2. wiki/sources

来源卡片层，用来回答：

- 这份材料从哪里来
- 它主要讲什么
- 它为什么重要
- 它目前在系统里扮演什么角色
- 它是否已经升格为正式 wiki 页面

### 3. wiki 正式页面

正式知识层，用来回答：

- 这个主题是什么
- 什么时候用
- 核心结构是什么
- 和其他页面有什么关系
- 当前边界和注意点是什么

## 默认工作流

### Ingest

当用户给出一份新资料时，默认按下面顺序处理：

1. 先确认资料进入 `raw/` 下的合适主题目录
2. 读取原始资料
3. 在 `wiki/sources/` 中建立来源页
4. 判断这份资料应该：
   - 只停留在 source 层
   - 还是继续升格为正式 wiki 页面
5. 如果升格：
   - 默认放到 `wiki/自我/`、`wiki/学习/`、`wiki/兴趣/`
   - 如果资料属于科研主线，默认提醒用户这应进入独立科研工作区，而不是在本仓新建科研目录
6. 更新 `wiki/index.md`
7. 追加更新 `wiki/log.md`

默认一次 ingest 一份资料，不做自动大批量改写，除非用户明确要求。

### Promotion 规则

满足以下特征的资料，更适合从 source 升格为正式 wiki 页面：

- 已经形成稳定方法
- 已经形成跨题型或跨章节的总结
- 已经形成长期有效的概念页
- 能回答未来会重复出现的问题

以下内容默认只停留在 source 层：

- 大量课程逐章笔记
- 大量导入型资料
- 纯目录型材料
- 暂时没有形成独立价值的零散记录

### Query

当用户提问时，默认按下面顺序处理：

1. 先读 `wiki/index.md`
2. 再读相关正式 wiki 页面
3. 如果正式页面不够，再读对应 `wiki/sources/`
4. 如果还不够，再回看 `raw/` 或旧 vault 原文

回答时尽量引用当前 wiki 中已经存在的页面路径。
如果一次问答产生了长期有效的新结论，应考虑把结论沉淀回 wiki，而不是只留在聊天记录里。

### Lint

定期检查 wiki 健康状况，重点看：

- 是否有重复页面
- 是否有过时结论
- 是否有 source 已经值得升格但还没升格
- 是否有正式页面缺少来源页
- 是否有孤立页面或弱连接页面缺少交叉引用
- 是否有迁移后遗留的旧路径表述
- `index.md` 和 `log.md` 是否落后于实际内容

## 写作规则

- 正式 wiki 页面默认按原子笔记思路维护
- 所有新页面默认使用中文
- 保持简洁，优先一页一事
- 不要把正式 wiki 页面写成原文摘抄
- 对于难理解的概念、定理、公式、方法页，优先补一个“最小工作例题”或“最小可用例子”，帮助用户把抽象结构落到实际场景里
- 这类例子应服务理解，不应把正式 wiki 页面重新写成题海、课本抄录或大段习题解析

### 原子笔记与链接规则

- `raw/` 中的资料默认只是原始材料，不视为原子笔记
- 正式 wiki 页面应尽量一页一事，一页只承载一个稳定概念、方法、问题、人物画像、主题判断或长期可复用结论
- 如果一页中已经混入多个可独立复用的知识点，优先拆页，再用 wikilink 连接，而不是继续堆在同一页
- 如果两个页面之间存在稳定语义关系，例如“定义-应用”“总览-分支”“方法-题型”“人物-事件”“主题-例子”，应主动补上 wikilink
- 双链和反向链接的目标不是为了把图谱做大，而是为了让知识之间的语义关系可见；不要为了图谱硬造链接
- 判断一个正式页面是否合格时，不只看内容是否完整，也看它是否已经进入现有知识网络，而不是孤立存在
- 正式页面优先写：
  - 定义
  - 用途
  - 核心结构
  - 边界
  - 必要时补一个最小工作例题 / 最小可用例子
  - 相关页
- source 页面优先写：
  - 来源
  - 内容概要
  - 当前角色
  - 是否升格
- 优先使用 wikilink 连接真正相关的页面
- 每次新增正式页面后，记得更新 `index.md`
- 每次 ingest、query 回写、lint 后，记得更新 `log.md`

## 用户个人偏好

- 在执行所有命令前，请确保有足够高的置信度再进行回答和执行
- 当用户是在学习一门新课、新知识或要求助手带学时，默认按以下讲解顺序组织内容：先讲定义 / 原理，再做通俗解释；如果涉及较难理解的公式、定理、机制或抽象概念，必须优先补充例子或例题来帮助理解
- 讲解单个知识点或单个章节时，保持结构完整、逻辑闭环；不要废话啰嗦，也不要为了简洁把关键推导、联系或结论省掉
- 如果用户要求创建某个知识点或章节的笔记，默认使用 Markdown 格式，并将 `.md` 文件放到对应主题文件夹中

## 学习内容讲解规则

- 面向初学或零基础场景时，优先采用“定义 / 原理 -> 文字解释 -> 例子 / 例题 -> 小结”的顺序讲解
- 其中“例子 / 例题”不是可选装饰，而是帮助用户真正理解抽象内容的核心环节；遇到难点时应主动补，不要等用户追问
- 如参考已有课程笔记结构，优先对齐 `raw/Linux/` 这类更贴近期末复习场景的写法：结构清楚、重点明确、例子服务理解，而不是空泛展开

## 遇到不确定情况时

如果遇到以下情况，先暂停并询问用户：

- 不确定某份资料该停留在 source 还是升格
- 不确定该放到 `学习/`、`自我/` 还是 `兴趣/`
- 需要批量处理大量历史资料
- 发现现有页面之间有明显冲突
- 用户希望把科研内容重新纳回本仓，或要把独立科研工作区内容迁进来

默认不要擅自创建新的大分类。
